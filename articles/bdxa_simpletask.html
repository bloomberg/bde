bdxa::SimpleTask: A Simple Experimental Coroutine Task Type

Summary

Starting with BDX 4.34.0, the header <bdxa_simpletask.h> introduces the class template bdxa::SimpleTask along with a supporting utility class, bdxa::SimpleTaskUtil. These types provide a lightweight mechanism for working with coroutines that represent deferred units of work.

A bdxa::SimpleTask<R> is an awaitable type that can be used as the return type of a coroutine. Such a coroutine does not begin executing immediately when it is called. Instead, the coroutine suspends before executing its body and returns a SimpleTask object to the caller. When the coroutine is later awaited or otherwise resumed, execution begins at the start of the coroutine body and continues until completion. At completion, a value of type R is produced via co_return. Coroutines that do not produce a value may return SimpleTask<void>.

Conceptually, a SimpleTask object acts as a handle to a deferred computation that can be resumed at a time chosen by the caller. If the coroutine eventually runs to completion, the co_await expression used to await the SimpleTask evaluates to the value provided by co_return.

One important property of SimpleTask coroutines is that they have no scheduler affinity. Each time a SimpleTask coroutine resumes after a suspension point, the coroutine continues executing on whichever thread triggered the resumption. That thread may differ from the thread that previously executed the coroutine, and the implications of this behavior are discussed in detail later in this article.

Example

Let’s consider a possibly asynchronous task that uses other APIs (possibly asynchronously) to query the value of the 1000th prime from some service. (Note that this example is available in its entirety as one of the usage examples in bdxa_simpletask.)

bdxa::SimpleTask<int> get1000thPrime()
{
    const int apiToken = co_await GetAPIToken(30782530);
    co_return co_await GetNthPrime(apiToken, 1000);
}

The function get1000thPrime is a coroutine, as indicated by the presence of the co_await and co_return keywords in its body rather than by its return type. All coroutines that return bdxa::SimpleTask suspend immediately when called. Evaluating the expression get1000thPrime() does not execute the first statement of the body. Instead, evaluating the expression returns a SimpleTask object that can later be used to resume execution.

One way to resume a SimpleTask coroutine is synchronously, using bdxa::SimpleTaskUtil::syncAwait. The syncAwait function blocks the calling thread until the coroutine completes, either by executing co_return, reaching the end of its body, or throwing an exception. For example:

void example1()
{
    bdxa::SimpleTask<int> task = get1000thPrime();
    const int result = bdxa::SimpleTaskUtil::syncAwait(bsl::move(task));
    assert(7919 == result);
}

If GetNthPrime queues a network request, the syncAwait call may block until an I/O thread receives and processes the response. That execution model demonstrates lazy execution, but it does not provide true asynchronous behavior. The synchronous blocking behavior therefore offers no advantage over representing the work as a bsl::function that is executed once by invoking it.

More commonly, users want the coroutine to begin executing while allowing other work to proceed whenever the coroutine suspends. That form of execution is achieved by awaiting the SimpleTask from another coroutine. For example:

bdxa::SimpleTask<void> print1000thPrime()
{
    bsl::cout << bsl::format("The 1000th prime is {}",
                             co_await get1000thPrime());
}

When print1000thPrime reaches the co_await expression, execution resumes the get1000thPrime coroutine, which runs until it reaches its next suspension point. If get1000thPrime has not yet completed, execution of print1000thPrime cannot continue, since the value required to complete the formatting operation is not yet available. As a result, the print1000thPrime coroutine also suspends, and control returns to the enclosing context.

At this point, two mechanisms for starting a SimpleTask coroutine have been introduced: awaiting the SimpleTask from another SimpleTask coroutine, and invoking syncAwait from non-coroutine code. Those two mechanisms are not sufficient to achieve true asynchronous execution. An outer coroutine that awaits an inner SimpleTask coroutine cannot continue while the inner coroutine remains suspended. Similarly, non-coroutine code that uses syncAwait must block until completion.

To support practical asynchronous execution, non-coroutine code must be able to asynchronously await awaitable objects such as SimpleTask. That capability is provided by additional libraries, such as the C++26 execution library (Senders and Receivers). Libraries of that kind rely on SimpleTaskUtil::asAwaitable to convert a SimpleTask into a generic awaitable that can participate in an asynchronous execution framework. The interaction between SimpleTask and such libraries is explained further in the Appendix.

Overview of Coroutine Return Types

A coroutine is a special kind of function that can suspend execution and later resume from the point of suspension. An overview of coroutines is available in the 2024 BDE Expo presentation bdla::Task: Understanding how to control coroutines, by example. The remainder of this article assumes familiarity with the material presented there.

The declared return type of a coroutine serves two distinct roles. First, since a coroutine is still a function, calling the coroutine produces an object whose type is the declared return type. Second, the return type determines key aspects of the coroutine’s execution by selecting the associated promise type.

As a result, achieving the desired behavior from a coroutine requires not only correctly implementing the coroutine body but also choosing an appropriate return type. Defining a custom coroutine return type involves significant boilerplate, so developers typically rely on return types provided by libraries.

BDX provides one such return type: bdxa::SimpleTask<R>. Declaring a coroutine with this return type specifies that calling the coroutine returns a SimpleTask<R> object and that the coroutine exhibits behaviors defined by the bdxa_simpletask component. One such behavior is immediate suspension before the coroutine body begins executing. If those semantics are not appropriate, SimpleTask should not be used.

Summary of bdxa::SimpleTask Coroutine Behavior

A coroutine that returns bdxa::SimpleTask<R> has the following properties:

  • Memory for the coroutine frame is allocated using the currently installed default allocator, or a user-specified allocator if one is provided. A user specifies an allocator by declaring the coroutine such that its first parameter has type bsl::allocator_arg_t and its second parameter is a bsl::allocator type.

  • Calling the coroutine returns immediately without executing the body. The body begins executing only when the coroutine is resumed.

  • The coroutine completes either by executing co_return or by throwing an exception. If R is void, reaching the end of the body is equivalent to co_return. The resulting value or exception is stored for later retrieval.

  • The coroutine is ill formed if it contains a co_yield expression. SimpleTask coroutines can produce only a single result.

  • When the coroutine completes, control returns to the coroutine that originally resumed it.

  • If R is allocator-aware, the allocator used to allocate the coroutine frame is also used to construct the result object. For example, if R is bsl::vector<int>, the vector returned by co_await or syncAwait uses the same allocator as the coroutine frame. The allocator used for the coroutine frame does not implicitly propagate to coroutines invoked by the original coroutine.

Awaiting bdxa::SimpleTask

Any coroutine that returns bdxa::SimpleTask<R> may co_await an rvalue of type bdxa::SimpleTask<S>, where S may be the same as or different from R. Awaiting a SimpleTask suspends the awaiting coroutine and resumes the awaited coroutine. When the awaited coroutine completes, the awaiting coroutine is immediately resumed, and the co_await expression either yields a value of type S or propagates an exception.

As noted earlier, bdxa::SimpleTask coroutines have no scheduler affinity. When such a coroutine suspends and is later resumed, execution may continue on a different thread, potentially from a different thread pool. That behavior often occurs when a coroutine suspends while waiting for I/O and is resumed by an I/O thread that detects completion.

The absence of scheduler affinity can produce surprising or undesirable results. An I/O thread may end up executing expensive computations in the coroutine body until the next suspension point, delaying the I/O thread’s primary responsibility of handling additional input. In addition, using thread-local variables or APIs that rely on thread-local storage inside a SimpleTask coroutine is dangerous. Accessing a thread-local object before and after a suspension point may refer to different instances of that object.

Adding general-purpose scheduler affinity would significantly increase the complexity of SimpleTask. Users who require scheduler control may instead benefit from the forthcoming BDXA execution library, which is modeled after the C++26 execution library. That library will provide a Task type that stores a scheduler and ensures that coroutine resumption always occurs on the associated scheduler.

SimpleTask can be viewed as a degenerate form of such a Task, in which work is completed inline without explicit scheduling. As a result, a SimpleTask coroutine written today is expected to interoperate smoothly with Task in the future, and migrating a coroutine from SimpleTask to Task should be straightforward when the latter becomes available.

Coroutines with non-SimpleTask return types can also await a SimpleTask, but only after wrapping the SimpleTask with bdxa::SimpleTaskUtil::asAwaitable. The asAwaitable function enables SimpleTask coroutines to interoperate with other coroutine types and execution frameworks. That interoperability is essential for true asynchronous execution, since SimpleTask alone cannot be resumed asynchronously from non-coroutine code.

Appendix: Asynchronous Execution of SimpleTask Coroutines

This appendix explains how bdxa_simpletask fits into a broader asynchronous execution framework such as Senders and Receivers. Understanding the material in this section is not required to use such frameworks with SimpleTask, but the discussion may help clarify how the pieces fit together.

Asynchronous resumption refers to resuming a coroutine from its suspension point, allowing the coroutine to execute until it reaches the next suspension, and then returning control to the resumer. During that execution window, the coroutine may initiate background work that will eventually resume the coroutine again. Although bdxa_simpletask does not directly provide a mechanism to asynchronously resume a SimpleTask coroutine, indirect mechanisms can be used to achieve that behavior.

Correct asynchronous execution requires careful lifetime management. Control returns to the resumer when the coroutine suspends, and the coroutine may later be resumed by another thread. Destroying the coroutine before final completion under those conditions results in undefined behavior. A separate mechanism is therefore required to notify the owner when the coroutine has completed.

In C++, asynchronous resumption is performed by calling resume on a std::coroutine_handle. Since SimpleTask does not expose the coroutine handle that it owns, asynchronous resumption must be mediated by another coroutine. That intermediary coroutine awaits the SimpleTask and exposes its own coroutine handle to non-coroutine code. When the SimpleTask completes, it resumes the intermediary coroutine, which moves responsibility for lifetime management up one level.

The SimpleTaskUtil::asAwaitable function is essential to this design, since the function enables non-SimpleTask coroutines to await SimpleTask coroutines.

For example, the Senders and Receivers library uses an internal coroutine in its implementation of connect. That internal coroutine allows any awaitable, including an awaitable backed by a coroutine, to be treated as a sender and resumed asynchronously. When the internal coroutine is resumed—indicating, in the case of a SimpleTask awaitable, that the SimpleTask has completed—the internal coroutine suspends again and invokes the receiver’s completion function. That completion propagates through a chain of operation states until execution reaches user code, at which point it is safe to destroy the SimpleTask. Since the internal coroutine is not exposed to the user, SimpleTask integrates seamlessly with sender algorithms such as when_all.
